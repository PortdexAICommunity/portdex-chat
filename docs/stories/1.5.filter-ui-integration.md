# Story 1.5: Create UI for filter controls and integrate with existing product card display

## Status

Ready for Review

## Story

As a sourcing user,
I want a unified and intuitive filter interface that allows me to apply multiple filters simultaneously,
so that I can efficiently refine my product search results and find exactly what I'm looking for.

## Acceptance Criteria

1. A filter panel is accessible from the product display area that allows users to apply all available filters (price range, MOQ, supplier verification, ratings).
2. Users can apply multiple filters simultaneously and see the combined results in real-time.
3. Filter controls are organized in a logical, user-friendly manner with clear labels and instructions.
4. Applied filters are visually indicated, and users can easily clear individual filters or all filters at once.
5. The filter panel does not interfere with the chat interface or product card display.
6. Filter state is maintained during the chat session but not persisted between sessions.

## Dev Notes

- Data Models
  - Product artifacts include all necessary fields for filtering: priceRange, moq, supplierName, supplierUrl, rating, trustMetrics [Source: prd.md#product-artifact-display, prd.md#supplier-trust-metrics]
  - No internal product tables. Product data is transient and fetched live via MCP. [Source: prd.md#data-models]
  - Normalized Product Artifact (example fields): title, priceRange, moq, supplierName, supplierUrl, rating, buyerInterest, trustMetrics? (yearsActive, reorderRate, verifiedBadges[]), retrievedAt. [Source: prd.md#product-artifact-display, prd.md#supplier-trust-metrics]

- API Specifications
  - Backend orchestrates calls to AI layer which triggers MCP when product data is required. [Source: architecture.md#2.-data-&-request-flow]
  - MCP layer is responsible for crawling/scraping/API calls and returns an aggregated list. [Source: architecture.md#mcp-layer]
  - Results should be normalized for UI consumption, independent of source. [Source: prd.md#product-artifact-display]
  - MCP requests should include all active filter parameters [Source: stories/1.3.price-range-moq-filtering.md, stories/1.4.supplier-verification-rating-filters.md]

- Component Specifications
  - Chat UI is primary input surface; product cards appear alongside chat feed (not replacing it). [Source: prd.md#user-experience]
  - Filter controls should appear contextually, not cluttering the main UI [Source: prd.md#ui-ux-considerations]
  - Use existing UI components from shadcn/ui for consistency [Source: architecture.md#1.-system-components-&-technologies]
  - Follow minimalist, usability-focused design principles [Source: prd.md#ui-ux-considerations]

- File Locations (Project uses Next.js with app directory)
  - Filter panel component: Likely in `components/` directory
  - Integration with product card display: `app/(chat)/` and related components
  - Filter state management: Likely in `app/(chat)/api/chat/route.ts` or related session management

- Testing Requirements
  - UI test filter panel: layout, responsiveness, interaction with product cards
  - Integration test multiple filter combinations: ensure all filter types work together correctly
  - Unit test filter state management: combining multiple filter parameters, handling edge cases

- Technical Constraints
  - Serverless-first; use Next.js API routes. [Source: architecture.md#4.-key-architectural-decisions]
  - Do not persist product data; only chat history is stored. [Source: architecture.md#4.-key-architectural-decisions]
  - Filter state should be maintained in session memory only, not persisted [Source: prd.md#chat-history-persistence]
  - Follow existing UI patterns and conventions [Source: architecture.md#1.-system-components-&-technologies]
  - Ensure performance is not significantly impacted by multiple filters [Source: docs/prd/epic-1-advanced-filtering.md#risk-mitigation]
