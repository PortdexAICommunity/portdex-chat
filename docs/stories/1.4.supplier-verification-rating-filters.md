# Story 1.4: Add supplier verification and rating filters to the product search

## Status

Ready for Review

## Story

As a sourcing user,
I want to filter product search results by supplier verification status and ratings,
so that I can quickly find products from trusted suppliers with good ratings.

## Acceptance Criteria

1. Users can filter products by supplier verification status (verified/unverified suppliers).
2. Users can filter products by supplier ratings (e.g., 4 stars and above).
3. Filters are applied in real-time to the product data returned by the MCP layer.
4. Filtered results are displayed in the product card artifacts alongside the chat.
5. Users can clear or modify filters to see different product results.
6. Filter state is maintained during the chat session but not persisted between sessions.

## Dev Notes

- Data Models
  - Product artifacts already include supplier trust metrics and ratings from previous stories [Source: prd.md#supplier-trust-metrics]
  - Trust signals include: years active, reorder rate, verification badges [Source: prd.md#supplier-trust-metrics]
  - No internal product tables. Product data is transient and fetched live via MCP. [Source: prd.md#data-models]
  - Normalized Product Artifact (example fields): title, priceRange, moq, supplierName, supplierUrl, rating, buyerInterest, trustMetrics? (yearsActive, reorderRate, verifiedBadges[]), retrievedAt. [Source: prd.md#product-artifact-display, prd.md#supplier-trust-metrics]

- API Specifications
  - Backend orchestrates calls to AI layer which triggers MCP when product data is required. [Source: architecture.md#2.-data-&-request-flow]
  - MCP layer is responsible for crawling/scraping/API calls and returns an aggregated list. [Source: architecture.md#mcp-layer]
  - Results should be normalized for UI consumption, independent of source. [Source: prd.md#product-artifact-display]
  - Extend MCP request schema to include optional filter parameters for supplier verification and ratings [Source: stories/1.2.mcp-integration-live-product-listings.md]

- Component Specifications
  - Chat UI is primary input surface; product cards appear alongside chat feed (not replacing it). [Source: prd.md#user-experience]
  - Filter controls should appear contextually, not cluttering the main UI [Source: prd.md#ui-ux-considerations]
  - Use existing UI components from shadcn/ui for consistency [Source: architecture.md#1.-system-components-&-technologies]

- File Locations (Project uses Next.js with app directory)
  - MCP adapter: `lib/ai/mcp/adapter.ts` (extend with filtering capabilities)
  - Chat UI components: `app/(chat)/` and `components/` directories
  - Filter state management: Likely in `app/(chat)/api/chat/route.ts` or related session management

- Testing Requirements
  - Unit test MCP adapter with filter parameters: request formatting, error handling
  - Integration test API route flow: when filters are applied, MCP is called with appropriate parameters
  - UI test filter controls: input validation, real-time filtering behavior

- Technical Constraints
  - Serverless-first; use Next.js API routes. [Source: architecture.md#4.-key-architectural-decisions]
  - Do not persist product data; only chat history is stored. [Source: architecture.md#4.-key-architectural-decisions]
  - Filter state should be maintained in session memory only, not persisted [Source: prd.md#chat-history-persistence]
  - Gracefully handle cases where trust metrics are not available from MCP sources [Source: prd.md#supplier-trust-metrics]
